# clodex — v0.2 debt

Known, adjudicated, and deliberately not in v0.1. Each entry says what it is,
why it did not block, and what closing it would take. Sources: the build
thread's adjudication at the review cap, the v0.1 pilot
(`pilot-notes-v0.1.md`), and the work that resumed the pilot on 2026-08-11.

Nothing here is a suspicion. Every item was reproduced or read off the code.

## Open

### 1. The plan-review loop has no autonomous exit

The pilot's headline finding, and the reason it parked. Every fix to a
substantive finding is a material amendment; every material amendment re-opens
the review loop; and `fixed` is the only disposition an autonomous operator
holds, because `accepted` and `rejected` are the user's. A sufficiently thorough
reviewer therefore keeps the loop open indefinitely — 5 rounds, 26 findings, all
of them true, no convergence.

Two changes would close it:

- A `deferred-to-build` disposition for findings that are true but are
  implementation detail rather than plan defects. Two of round 5's three were
  exactly that.
- Key the 3-round cap to the **severity trend** rather than the round count. The
  pilot's counts fell 8, 6, 5, 4, 3 while severity did not (3 high → 0 → 0 → 3
  high → 1 high), and the cap's advice — "a fourth round is not the answer" —
  was wrong: round 4 caught a defect that would have shipped silent data
  corruption.

The engine half is now in place: `findings[].severity` and `findings[].round`
reach the manifest, so the trend is readable from `rebuild` and from
`clodex_state.py status`. What is missing is `clodex-plan` §8 using them.

### 2. The change boundary is one-directional

clodex spends real effort making sure a run never commits the user's work.
Nothing protects the run's work from a concurrent actor — and during the pilot a
second session in the same repo swept the run's in-progress plan file into its
own commit. Provenance was unambiguous: the committed blob hashed to the value
the manifest had recorded for plan v4.

Run state survived only because preflight's literal `.gitignore` remedy had been
worked around with a nested ignore file inside the run directory. Had the
documented remedy been used, 56 events would have landed in someone else's
commit.

Minimum fix: `clodex-build` and `clodex-ship` re-hash the plan file against
`plan.hash` (build already does) **and** check whether any run-owned path became
tracked by a commit the run did not make. Detecting it is cheap; discovering it
at ship is not. The preflight remedy should also prefer the nested ignore file,
which is self-contained and cannot collide with another session's edit to
`.gitignore`.

### 3. clodex-ship has no committed test harness

The 196 checks the ship skill was built against lived in a session scratchpad
and were never committed, so every later change to a 2000-line document is
unverified by them. The 2026-08-11 fixes above were checked by a purpose-built
harness that extracts the document's own scripts and runs them against synthetic
repos — 12 checks, exploit and control for each — which is the right shape and
should be committed and grown rather than rebuilt each time.

The other four stage skills are in the same position.

### 4. Smaller items, recorded at the build thread's review cap

- **`profile.schema.json` is an unpinned, security-relevant input.** §6 trusts
  the *field set* from the skill install. It fails closed when the file is
  missing, unreadable, or empty of properties, but cannot detect a deliberately
  shortened one.
- **A profile key the schema does not declare is never compared.**
- **A dead `"-a m"` entry** in the forbidden-argv predicate; it can never be a
  single argv element.
- **No §5 pre-check for a changelog the repo has never had** (the §7.2 side is
  handled).
- **`resolve()` handles only `str` and `list`**, and blank added lines are
  exempt from the changelog stray test.
- **The table-versus-script mismatch** for a repo whose only proof is a
  deployment list.
- **Ship's three local ids have no profile entry** to be cross-checked against —
  stated in §6 as a known limitation.

### 5. Pilot friction not otherwise listed

- A single review round can exceed the harness's maximum tool timeout (600 s);
  nothing in the skill warns of it, and every round after the first had to be
  launched detached.
- The runner's one-command resume line goes to stderr, which is exactly what a
  kill destroys. It belongs in the envelope.
- A resume overwrites the interrupted envelope, so the envelope under-reports a
  resumed round. The manifest side is fixed — legs are recorded separately and
  sum to the truth — but the envelope on disk still lies.
- Envelopes are not keyed to the run: two runs in one repo interleave in the
  same directory.
- `--untracked-files=all` expanded a 19-path dirty set to 730, and the
  instruction to show the user every dirty path became unusable. Keep the rule,
  group by directory for display.
- One `commands.test` slot for a polyglot repo, so two suites are composed with
  `&&` and a failure cannot be attributed without re-running.
- The profile's `work_on_default: false` is necessarily committed to the branch
  it forbids.

## Found completing the pilot, 2026-08-11 (second sitting)

The run reached `not-deployed` and closed. These are what it cost to get there.

### 6. §7's boundary check misattributes a concurrent session's work, and its remedy is destructive

`clodex-build` §7 compares the tree against `git.dirty_at_start`, a snapshot
taken when the run **opened**. In a repo with a concurrent session that snapshot
is stale within minutes. This run's check printed `STOP — 9 path(s) the contract
does not allow`; **none of the nine was the implementer's.** Eight were the other
session's files, created or modified between the run opening at 13:07 and the
batch running at 17:14; the ninth was this run's own plan amendment, owned by
batch 2. Proven two independent ways: every one of the nine has an mtime before
the implementer's window opened, and the implementer's own event stream names
exactly two paths, both owned.

The hazard is what §7 says to do next. For a path marked `NOT owned by this
batch` it prescribes `git checkout --` for tracked files and `mv` for untracked
ones. Followed literally here that would have reverted six of another session's
working files and moved two of their untracked plan documents out of the tree —
unrecoverable, since untracked files have no committed state to restore.

*Fix:* compare against the tree **as it was when the implementer started**, not
when the run opened — write a pre-invocation snapshot into `$RUN_DIR` before each
`batch:opened` and diff against that. Consult the implementer's own event stream
as a second source before any restore is offered, and never present a restore
command for a path the run cannot prove it touched.

### 7. The micro-gate is not attributable in a shared tree, and a red one has no legal remedy

`commands.test` runs the whole repo suite from the repo root. A concurrent
session edited `scripts/build_demo_library.py` two minutes after the implementer
finished, referencing a symbol it had not defined yet; the gate went from green
to 22 failures and 12 errors, all in one file, none of them this run's.

`clodex-build` §8 offers exactly two remedies for a red gate — fix it, or re-run
the implementer — and **both are forbidden**, because the failing file is another
session's dirty work that §2 and §7 make untouchable. `clodex-verify` forbids the
third option, recording a red gate as debt. A run in this position has no legal
move.

Resolved by running the gate in a **clean worktree** holding the committed branch
state plus the batch's owned files — which is what the batch actually ships.
Green there, and it also produced the only test counts attributable to this
release rather than to whatever else was on disk.

*Fix:* make that the documented gate for a repo with concurrent sessions. It is
more correct than the in-tree gate even when the tree is clean, because it proves
the gate against what ships.

### 8. An authorization payload error is uncorrectable without amending the plan

The release authorization recorded the changelog rollup as the new row **plus**
the row it is inserted above. §7.2's containment test correctly refused it:
removing that block leaves the file one row short of its pre-release state, so it
reads as a foreign edit. The authorization was already appended, and it is
unsatisfiable — no file content can pass that test.

There is no correction path. A second `approval:granted` leaves **two** standing
release authorizations and §10 blocks on that; only a plan amendment revokes the
first. So a ship-payload typo was fixed by amending the plan — which is the
mechanism §5 names, but it is the wrong shape for the problem.

*Fix:* either a `approval:revoked` scope, or let a later `release-authorization`
supersede an earlier one the way `plan:amended` supersedes a plan hash. The
validator should also refuse an authorized changelog text that cannot satisfy the
containment test — it can check that at authorization time, which is the whole
point of that gate.

### 9. Nothing tells the plan author or the plan reviewer what the release-owned set is

Batch 2 of the approved plan owned `docs/2-changelog/w3_v1.7.0.md`,
`docs/2-changelog/changelog_table.md` and `package.json` — the profile's
`changelog.path` and `version.source`, which `clodex-build` §2 categorically
forbids. **Six rounds of plan review did not catch it**, and could not have:
`clodex-plan` never states the release-owned set, and §8's review prompt never
asks. The cost was an eighth plan version, a seventh review round and a
re-approval, all discovered at the first line of build.

*Fix:* `clodex-plan` §5 should print the release-owned set beside the Batches
table the way `clodex-build` §2 does, and §8's prompt should ask whether any
owned path is release-owned. Cheap, and it closes the whole class.

### 10. A run cannot re-bound itself when the default branch advances under it

`git.start_head` is written once at open and no event changes it. Main advanced
7 commits between this run opening and its build stage, so ship §3(b) — which
bounds the release as `start_head..HEAD` — reported all 7 as unowned commits
needing disposition, alongside the one the run legitimately made at verify.
Branching from `start_head` instead would make §3(b) clean but break the repo's
own `merge-main-ff` convention, which needs a fast-forwardable branch.

*Fix:* bound the release at the merge-base of the run's branch and the default
branch rather than at `start_head`. It is derivable and needs no new state.
